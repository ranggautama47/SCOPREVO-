## 4. Proposed Database Design

### 4.1 `project_document` Table

```sql
CREATE TABLE project_document (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id UUID NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  account_id UUID NOT NULL REFERENCES account(id) ON DELETE CASCADE,  -- denormalized for RLS/ownership
  filename TEXT NOT NULL,                    -- original filename
  mime_type TEXT NOT NULL,                   -- 'application/pdf', 'application/vnd.openxmlformats-officedocument.wordprocessingml.document', 'text/markdown'
  size_bytes BIGINT NOT NULL,                -- file size
  storage_path TEXT NOT NULL,                -- Supabase Storage object path (bucket/uuid.ext)
  extracted_text TEXT,                       -- parsed text content (nullable if parsing failed)
  extraction_status TEXT NOT NULL DEFAULT 'pending',  -- 'pending' | 'completed' | 'failed'
  extraction_error TEXT,                     -- error message if failed
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Indexes
CREATE INDEX idx_project_document_project ON project_document(project_id);
CREATE INDEX idx_project_document_account ON project_document(account_id);

-- Constraints
ALTER TABLE project_document ADD CONSTRAINT chk_mime_type
  CHECK (mime_type IN ('application/pdf', 'application/vnd.openxmlformats-officedocument.wordprocessingml.document', 'text/markdown'));
ALTER TABLE project_document ADD CONSTRAINT chk_size_max
  CHECK (size_bytes <= 10485760);  -- 10 MB
ALTER TABLE project_document ADD CONSTRAINT chk_extraction_status
  CHECK (extraction_status IN ('pending', 'completed', 'failed'));

-- Updated_at trigger (mirror pattern if other tables adopt it later)
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
CREATE TRIGGER update_project_document_updated_at
  BEFORE UPDATE ON project_document
  FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();
```

### 5.3 Controller (`controllers/document.controller.ts`)

```typescript
import { Request, Response, NextFunction } from 'express';
import { documentService } from '../services/document.service';
import { UnauthorizedError, NotFoundError } from '../middleware/error.middleware';

function requireAccountId(req: Request): string { ... }

export const documentController = {
  async listDocuments(req: Request, res: Response, next: NextFunction) {
    try {
      const accountId = requireAccountId(req);
      const { projectId } = req.params;
      const docs = await documentService.listDocuments(projectId, accountId);
      res.status(200).json({ documents: docs });
    } catch (err) { next(err); }
  },

  async uploadDocument(req: Request, res: Response, next: NextFunction) {
    try {
      const accountId = requireAccountId(req);
      const { projectId } = req.params;
      const file = req.file;
      if (!file) throw new BadRequestError('No file uploaded');
      const doc = await documentService.uploadDocument(projectId, accountId, file);
      res.status(201).json({ document: doc });
    } catch (err) { next(err); }
  },

  async deleteDocument(req: Request, res: Response, next: NextFunction) {
    try {
      const accountId = requireAccountId(req);
      const { projectId, documentId } = req.params;
      await documentService.deleteDocument(projectId, documentId, accountId);
      res.status(204).send();
    } catch (err) { next(err); }
  },
};
```

### 5.3 Service (`services/document.service.ts`)

- `uploadDocument(projectId, accountId, file)` — verify ownership, check quota (max 3), upload to Supabase Storage, create DB row with `extraction_status: 'pending'`, queue/trigger extraction
- `deleteDocument(projectId, documentId, accountId)` — verify ownership, delete from Storage, delete DB row

## 7. File Parsing Strategy

### 7.1 Candidate Libraries (Server-Side Only)

| Format | Library | Size Impact | Security Notes |
|--------|---------|-------------|----------------|
| PDF | `pdf-parse` (unmaintained) or `pdf2pic` + `tesseract` or `@pdf-lib/pdf-parse` fork | ~2-5 MB | No eval, pure JS; validate MIME + magic bytes |
| DOCX | `mammoth` | ~1 MB | Pure JS, no native deps; safe |
| MD | `marked` or `remark` | ~500 KB | Pure JS; sanitize if rendering HTML |

**Recommended stack:**
- `pdf-parse-fork` (actively maintained fork) or `pdfjs-dist` (larger, ~10 MB)
- `mammoth` for DOCX
- `marked` for MD (parse to text, not HTML)

**Bundle size estimate:** +3-5 MB total (acceptable for Node backend).

**Client-side parsing: REJECTED** — bundle bloat, security risk (malicious files in browser), no server validation.

### 7.2 Parsing Pipeline

```typescript
// services/document-extraction.service.ts
async function extractText(file: Express.Multer.File): Promise<string> {
  switch (file.mimetype) {
    case 'application/pdf':
      return extractPdfText(file.buffer);
    case 'application/vnd.openxmlformats-officedocument.wordprocessingml.document':
      return extractDocxText(file.buffer);
    case 'text/markdown':
      return file.buffer.toString('utf-8');  // MD is plain text
    default:
      throw new Error('Unsupported MIME type');
  }
}
```

**Async processing:** Parse synchronously in upload request (files ≤ 10 MB, parsing < 2s). For larger files, use background job (not needed for MVP).

## 9. Token / Context Limits (With Justification)

### 9.1 Current LLM Call Analysis

From `ai.service.ts:102-109`:
- No `max_tokens` specified → provider default (typically 4096-8192 output)
- No context window documented in `env.ts` or provider config
- Temperature 0.1 (deterministic)

### 9.2 Provider Context Windows (External Knowledge)

| Provider/Model | Context Window | Notes |
|----------------|----------------|-------|
| Google Gemini 1.5 Flash | 1M tokens | Primary (via OpenAI-compatible endpoint) |
| OpenRouter (varies) | 4K-128K | Fallback, model-dependent |

**Assumption:** Minimum usable context = 4,000 tokens (conservative for fallback).

### 9.3 Recommended Limits

| Parameter | Value | Justification |
|-----------|-------|---------------|
| Max file size | 10 MB | Matches DB constraint; PDF text ~1 char/byte |
| Max extracted chars/file | 8,000 chars (~2K tokens) | Leaves room for feedback + prompt + output |
| Max total context chars | 24,000 chars (~6K tokens) | 3 files × 8K; fits in 4K fallback window with headroom |
| Truncation strategy | Per-file truncation at 8K, then drop oldest if >3 files | Simple, deterministic |

**Implementation:**

```typescript
function truncateContext(documents: Document[], maxTotalChars = 24000, maxPerFile = 8000): Document[] {
  const truncated = documents.map(d => ({
    ...d,
    extractedText: d.extractedText.slice(0, maxPerFile)
  }));
  let total = truncated.reduce((sum, d) => sum + d.extractedText.length, 0);
  while (total > maxTotalChars && truncated.length > 0) {
    const removed = truncated.shift()!;
    total -= removed.extractedText.length;
  }
  return truncated;
}
```

## 11. Anti-Hallucination Strategy

### 11.1 Grounding Rule Priority (SYSTEM_PROMPT addition)

```
SYSTEM RULES (HIGHEST PRIORITY):
1. You are SCOPREVO Revision Intelligence Engine. Analyze client feedback and extract actionable revision items.
2. Use ONLY information from: (a) PROJECT CONTEXT documents, (b) CLIENT FEEDBACK text.
3. NEVER invent project facts, features, or requirements not present in context or feedback.
4. If context + feedback is insufficient to confidently classify an item → NEEDS_REVIEW with reason "Insufficient context to determine scope".
5. OUT_OF_SCOPE requires explicit reason citing what in feedback/context places it out of scope.

PROJECT CONTEXT (SECOND PRIORITY):
- Attached documents define the project's agreed scope, features, and constraints.
- Treat document content as ground truth for what exists in the project.

CLIENT FEEDBACK (THIRD PRIORITY):
- The immediate request being analyzed.
- May reference things not in context — classify those as NEEDS_REVIEW.

OUTPUT FORMAT (UNCHANGED):
{"summary":"...","items":[{"description":"...","scope":"IN_SCOPE"},{"description":"...","scope":"OUT_OF_SCOPE","reason":"..."},{"description":"...","scope":"NEEDS_REVIEW","reason":"..."}]}
```

### 11.2 Explicit Limitations

- **Does NOT eliminate hallucination** — LLMs can still misinterpret context or fabricate links between context and feedback.
- **Mitigations**: Low temperature (0.1), strict JSON schema validation, NEEDS_REVIEW as safety valve.
- **No guarantee** — "sufficient context" is subjective; edge cases will still produce NEEDS_REVIEW (correct behavior).

## 12. Security Considerations

| Threat | Mitigation |
|--------|------------|
| **Malicious file content** (polyglot, embedded scripts) | MIME validation + magic bytes check (`file-type` lib); parse in sandboxed process if possible |
| **Oversized files** | 10 MB hard limit at multer + DB CHECK constraint |
| **MIME spoofing** | Validate magic bytes, not just `file.mimetype`; reject mismatches |
| **Duplicate uploads** | SHA-256 hash of content; unique constraint on `(project_id, content_hash)` |
| **Filename injection** | Sanitize filename (strip path traversal, null bytes); store original separately |
| **Storage access control** | Private bucket; server-side upload with service role; signed URLs only for download (if needed) |
| **Project ownership verification** | Every document operation checks `project.account_id = req.accountId` (existing pattern) |
| **Extracted-text injection** | Treat extracted text as untrusted; escape/limit length before prompt injection; no eval |
| **DoS via parsing** | Timeout on extraction (5s); file size limit; queue if needed |
